# Операции моста: заряд, отключения, защита устройств ввода (скрипты v4, 14.11.2026)

Документ описывает, как устроена одна операция моста:
- почему AirPods теряют связь и сколько раз;
- как обновляется заряд;
- как защищены Bluetooth-мышь и клавиатура;
- что остаётся ограничением архитектуры.

Всё, что отмечено «измерено», снято на тестовом ПК: AirPods Pro 3, MediaTek MT7922 `13d3:3622`, Windows 11 26200.

## 1. Одна операция = один цикл передачи адаптера

Каждая передача адаптера проходит через `HandoverCoordinator` (Core). Это касается переключения режима, точного заряда, тестов мастера и восстановления при запуске.

1. **Одна операция за раз.** Внутри процесса есть семафор. Между процессами (программа и `airpodsctl`) действует эксклюзивно открытый файл `%LOCALAPPDATA%\AirPodsControl\bridge\operation.lock`. Если процесс падает, Windows освобождает файл сама. Вторая операция отклоняется сразу, без побочных эффектов: итог `NotStarted`, в трассе `rejected_busy` или `rejected_locked`.
2. **Сначала проверки, потом отключение.** Порядок: блокировка → сопоставление адаптера → защита устройств ввода → подготовка (WSL, демон, скрипты). Только после этого — выключение радио → attach → операция → release → detach → включение радио. Последние три шага выполняются в `finally`, в том числе при ошибке и отмене.
3. **Без автоматических повторов.** Отсутствие эха (`sent`) — нормальный случай без A2DP, поэтому оно не вызывает ни повторной передачи, ни скрытого повтора команды. Раньше режим, выбранный, когда адаптер уже возвращался в Windows, запускал ещё одну передачу. Теперь его нет.
4. **Нажатия во время переключения.** Если адаптер ещё в WSL, новый режим отправляется по уже открытому каналу (последний выбор побеждает). Повтор того же режима игнорируется. Если адаптер уже возвращается, запрос отклоняется с сообщением «выберите ещё раз через несколько секунд», а не откладывается на потом. Горячие клавиши раньше в это время просто терялись. Кнопки панели на время переключения по-прежнему неактивны.
5. **Восстановление при запуске** выполняется только под той же блокировкой. Оно не может отсоединить адаптер, пока CLI или другой процесс его использует.

### Почему было два-три отключения: что показали трассы

Трасса каждой операции пишется в `%LOCALAPPDATA%\AirPodsControl\logs\bridge-trace-ГГГГММДД.log`. В каждой строке: ID операции, инициатор и время от начала. Источники:
- `App` — действия программы;
- `Windows` — наблюдения: состояние связи AirPods, радио, аудиоустройство AirPods;
- `Daemon` — этапы внутри WSL;
- `Linux` — события ядра: ACL connect/disconnect с причиной, index added/removed;
- `Aap` — принятые пакеты.

**Измерено: одно переключение, CLI, демон, 14.11.2026, `op1-3472`.**

| t, с | Источник | Событие | Кто вызвал |
|---|---|---|---|
| 4.29 | App | `radio_off_request` (только радио MT7922) | программа |
| 4.32 | Windows | связь AirPods пропала | следствие выключения радио |
| 4.54 | Windows | **аудиоустройство AirPods отключено** (обрыв звука №1) | следствие |
| 4.42–7.65 | App | `usbipd attach` (≈3,2 с, одна попытка) | программа |
| 7.37 | Windows | адаптер исчез из Windows (`no_adapter`) | переинициализация USB |

**Вывод из трасс.** Внутри одной операции звук пропадает ровно один раз: аудиоустройство Windows выключается один раз и включается один раз. Сами AirPods теряют связь дважды:
1. со связью с Windows, когда выключается радио;
2. со связью с Linux, когда выполняется release.

Между этими моментами они подключены к Linux. Каждый из этих переходов вызывает программа, лишних нет: одна попытка L2CAP, один ACL. Ещё одна такая же трасса (`op1-8bc9`, два режима за одну передачу) и чтение заряда (`op1-09b2`) показали то же самое: `attach=1 detach=1 audio_endpoint_off=1 audio_endpoint_on=1 linux_acl_connected=1 linux_acl_disconnected=1`.

**Откуда брались «два-три» отключения.** Это вывод по коду и логам; на слух проверить не мог.
- **Две потери связи AirPods** за одну передачу — неизбежны, пока один адаптер обслуживает два хоста.
- **Несколько отдельных операций подряд.** В логе программы три нажатия дали три полных цикла. Нажатия во время переключения не объединялись: горячие клавиши в это время отбрасывались.
- **Повторы подключения.** В прежнем пути через bluetoothd были повторы подключения (`connect attempt=2`) и повторы `power on`. Каждая неудачная попытка — это лишний пейджинг.
- **Мастер настройки** выполняет две отдельные операции: тест адаптера и тест AirPods. Каждая — свой цикл.
- **Запоздалое «disconnected»** от Windows после возврата адаптера. Это не новый обрыв, но в логе он выглядит как ещё одно отключение.

Ещё одна найденная проблема. Тест мастера и горячая клавиша могли наложиться друг на друга, а CLI и программа — работать одновременно. Тогда восстановление в одном процессе могло бы сделать detach адаптера посреди операции другого. Теперь это исключено.

### Ответ о режиме: парсер не меняли

По сырой трассе: после команды 0x0D пакетов 0x09 нет вообще. Неизвестные опкоды (0x08, 0x0C, 0x0E, 0x2B, 0x2E) приходят до команды и с режимом не связаны. Значит, «подтверждения, которое парсер не распознал» нет, и парсер не менялся. Итоги разделены так:

| Итог | Значение | Успех |
|---|---|---|
| `Confirmed` | AirPods прислали 0x09 0x0D с этим режимом | да |
| `Sent` | handshake подтверждён, команда записана, ответа нет (подтверждает канал, а не применение) | да, показывается как «sent … not confirmed by AirPods» |
| `NoResponse` | ни ответа на handshake, ни эха | нет |
| `TransportError` | канал не открылся или сломался при записи | нет |
| `NotStarted` | не начиналось: занято, защита устройств ввода, неясный адаптер | нет, Bluetooth не трогался |

## 2. Заряд

- **«Refresh battery» (BLE)** — радио не трогает. Ждёт до 8 с следующего рекламного пакета AirPods. BLE не позволяет запросить значение: если пакета нет, программа так и пишет. Последние значения остаются со временем получения и помечаются устаревшими: тусклые цифры, подсказка «received HH:mm:ss · no fresh data since then». Они никогда не заменяются нулём и не исчезают по таймауту, как было раньше.
- **«Exact (AAP)…»** — отдельное действие с предупреждением (диалог, по умолчанию «Нет»): Bluetooth отключится примерно на 10 с. Одна передача адаптера, операция демона `read`, команда не отправляется. Измерено (`op1-09b2`): L 48 %, R 46 %, кейс «—», звука нет 11,8 с.
- **При переключении режима** заряд берётся из той же AAP-сессии. Отдельного цикла ради заряда нет.

## 3. Защита мыши и клавиатуры

Перед любой передачей адаптера `InputDeviceScanner` делает две вещи.

1. **Находит кандидатов в дереве устройств ниже USB-узла этого адаптера:**
   - узлы Classic HID `BTHENUM\{00001124…}`;
   - узлы HID-over-GATT `BTHLEDEVICE\{00001812…}`;
   - сопряжённые Classic-устройства с Class of Device «peripheral» (реестр `BTHPORT\Parameters\Devices\<адрес>\COD`, читается без прав администратора).

   Такие же узлы под другим адаптером отмечаются как «не на этом адаптере».
2. **Проверяет, подключён ли каждый кандидат прямо сейчас:** WinRT `ConnectionStatus`, лимит 4 с на устройство. Сопряжённое, но отключённое устройство передачу не блокирует.

Решения:
- **Мышь или клавиатура подключены через этот адаптер** — блокировка до любых отключений.
- **Принадлежность или состояние определить не удалось** — статус `Unknown`. Он тоже блокирует: операция не объявляется безопасной.
- **Обход** возможен только явным решением:
  - в программе — отдельный диалог, доступный с клавиатуры, по умолчанию «Нет», открывается поверх остальных окон;
  - в CLI — отдельный флаг `--allow-input-loss`. Общий `--yes` (мастер) его не включает.
- **Мастер:** блокировка до начала теста не записывается как «тест адаптера провален».

Почему не перечисление ассоциированных конечных точек Windows: на тестовом ПК один такой запрос шёл 30 с, а с запросом Class of Device — больше 100 с или падал с `RPC_E_UNEXPECTED`.

Проверено: на этом ПК `airpodsctl bridge-check` за 0,6 с ответил `Clear`, Bluetooth-устройств ввода нет. **Блокировку с реальной мышью или клавиатурой проверить не на чем — требуется проверка на оборудовании.** Логика решения покрыта тестами.

### Выбор радио и адаптера

- **usbipd-устройство** выбирается по сохранённому instance id (`AdapterUsbInstanceId`), а не по VID:PID.
- **Радио Windows** — это интерфейс `USB\VID_13D3&PID_3622&MI_00\…`. Оно сопоставляется с USB-устройством по цепочке родителей в дереве устройств.
- **Выключается только радио этого адаптера:** WinRT `BluetoothAdapter.FromIdAsync(путь интерфейса).GetRadioAsync()`. Раньше выключалось «первое радио Bluetooth».
- **Несколько одинаковых адаптеров без сохранённого id** допустимы, только если радио Windows однозначно указывает на один из них. Иначе, как и при несопоставленном радио, операция останавливается до отключения.
- **Если активное радио Windows — другой адаптер**, его не трогают.
- **Detach** выполняется только по bus id: detach по hardware id задел бы и второй такой же адаптер.

## 4. Отдельный адаптер для постоянного моста — исследование, не проверено

Идея: дешёвый второй USB-адаптер постоянно подключён к WSL (`usbipd attach --auto-attach`). MT7922 остаётся у Windows вместе со звуком, мышью и клавиатурой. AAP-канал держится постоянно, переключение занимает доли секунды и обходится без обрывов.

| Вопрос | Что известно | Статус |
|---|---|---|
| Сопряжение | У второго адаптера свой адрес: ключ из Windows не подходит. Нужно отдельное сопряжение AirPods с Linux (кнопка на кейсе, `bluetoothctl pair`). AirPods помнят ограниченное число хостов | требуется проверка на оборудовании |
| Два соединения одновременно | AirPods держат связь с несколькими устройствами Apple. Пакет 0x2E (список подключённых устройств) приходит и нам. Держат ли они ACL с чужим хостом без звука, пока Windows играет звук, неизвестно | требуется проверка на оборудовании |
| Примут ли 0x0D от хоста без звука | По нашим трассам команда применяется и без A2DP. Но тогда AirPods не были подключены к другому источнику | требуется проверка на оборудовании |
| Не уведут ли звук | При подключении нового хоста AirPods могут переключить «владельца» соединения (control 0x06): звук может уйти из Windows | требуется проверка на оборудовании |
| Драйвер второго адаптера в WSL | Realtek (RTL8761B и др.) — `btusb`+`btrtl`, нужна прошивка `rtl_bt` в ядре (как MediaTek). Intel — `btintel` | собрать и проверить |
| Windows не должна взять второй адаптер | Windows использует одно радио. `usbipd bind` (один раз, с правами администратора) и `--auto-attach` держат второй адаптер в WSL | требуется проверка на оборудовании |

Пока эти пункты не проверены, схема **не объявляется рабочей**. Текущая архитектура с одним адаптером не меняется.

## 5. Что остаётся ограничением

- **С одним адаптером** звук пропадает на ≈12–15 с на операцию (измерено 11,8–14,6 с), а AirPods дважды меняют связь. Сократить можно только время, не число переходов.
- **Самые долгие этапы** вне нашего контроля:
  - `usbipd attach` ≈3 с;
  - пейджинг AirPods из Linux 1,4–4,7 с, сильно колеблется;
  - возврат AirPods к Windows 1,3–3,4 с с подталкиванием.
- **Подтверждения режима нет**: без A2DP AirPods не присылают 0x09.
- **BLE-заряд** зависит от того, рекламируют ли AirPods; запросить его нельзя.
- **Тесты мастера** — две отдельные операции.
- **Не проверено на оборудовании:**
  - блокировка при реальной BLE- или Classic-мыши;
  - несколько одинаковых адаптеров;
  - новые кнопки заряда и диалоги в окне программы. Портативная сборка в `dist` ещё старая: проверены CLI и тот же код провайдера.
- **Старая сборка программы**, если она запущена, не знает о межпроцессной блокировке. После обновления это закрыто.

## 5a. Режимы удержания ножки (Settings → Press and hold)

Цель: пользователь без iPhone/Mac один раз записывает в AirPods набор режимов, между которыми переключает удержание
ножки (в том числе Off), и дальше выбирает их без приложения и без моста.

**Протокол** (LibrePods `docs/control_commands.md`, `docs/AAP Definitions.md` → «Configure Stem Long Press»). Всё это
control-команды, opcode пакета `0x0009`; ниже — control ID (байт 6), а не opcode:

| Control ID | Значение | Что делает приложение |
|---|---|---|
| `0x1A` ListeningModeConfigs | маска: Off `0x01`, ANC `0x02`, Transparency `0x04`, Adaptive `0x08` (не равна значениям `0x0D`!) | пишет выбранный набор |
| `0x34` Allow Off Option | `01` разрешить, `02` запретить | шлёт `01`, только если Off в наборе; `02` не шлёт никогда |
| `0x16` ClickHoldMode | data1 — правая ножка, data2 — левая; `01` управление шумом, `05` Siri | только читает; не меняет никогда |
| `0x0D` ListeningMode | текущий режим | не отправляется (текущий режим не меняется) |

Допустимый набор: только эти четыре бита, **не меньше двух режимов** (все значения 0x1A в источниках содержат ≥ 2 бита;
одиночный режим сделал бы удержание бессмысленным), Adaptive/Off — только если они есть у модели.

**Одна операция** `HoldCycle` = одна передача адаптера и одна AAP-сессия демона: `read` с `wait_controls`
(до 3 с ждёт 0x1A/0x34/0x16) → решение `OffCyclePlanner` в Windows → `configure` (0x34, затем 0x1A, каждая не больше
одного раза, без повторов) → `release`. Защита мыши/клавиатуры, сопоставление радио и адаптера, межпроцессная
блокировка и восстановление — общие с переключением режима. Слияние нажатий горячих клавиш в эту операцию не принимается.

**Итог разделён на три факта:** команды отправлены / подтверждены ответом AirPods (эхо 0x09 с тем же значением) /
сохранение после переподключения — приложением **не проверяется никогда** (`PersistenceVerified = false`). Без ответа:
«Settings sent. Check whether Off now appears when you press and hold a stem.» Автоповторов нет.

**Окно настроек.** Четыре независимых флажка — это *желаемый набор* (хранится в `settings.json`, `HoldCycleModes`).
Отдельной строкой — что известно об AirPods (`bridge.json`: `HoldCycleReported` — что сообщили сами AirPods,
`LastOffCycle` — что записало приложение и чем кончилось): «Current AirPods set: unknown.» / «AirPods reported: …» /
«AirPods confirmed: …». Запись — только кнопкой «Apply to AirPods» после предупреждения (по умолчанию «No»), не при
изменении флажков, не при запуске и не при подключении.

**Проверено на железе (AirPods Pro 3, 14.11.2026):** `bridge-enable-off --keep-current` — одна передача, 9 пакетов от
AirPods (`0x2B, 0x2E, battery, 0x08, 0x0C, 0x0E, 0x2E, ear`), **ни одного 0x09**: текущий набор, Allow Off и действие
удержания не сообщаются. Поэтому ничего не записано (как и задумано), набор надо выбирать явно.
Затем из настроек (Apply to AirPods) записаны три набора: `0x07` (Off, ANC, Transparency), `0x09` (Off, Adaptive),
`0x05` (Off, Transparency) — каждый одной передачей, итог «Sent» (ответа 0x09 нет). Пользователь проверил удержанием
ножки: наборы **применяются**, Off появляется в цикле.
**Не проверено систематически:** сохранение после закрытия приложения, переподключения и кейса (шаги 3–5 ниже).

**Инструкция для аппаратной проверки (шаги 1–2 выполнены, 3–5 — нет):**
1. Settings → Press and hold: отметить, например, Off + ANC + Transparency → Apply to AirPods → Yes.
2. Удерживать ножку: появляется ли Off в цикле, остались ли ANC и Transparency (с обеих ножек).
3. Закрыть приложение (`AirPodsControl.exe --exit`) — повторить п. 2.
4. Отключить/подключить AirPods в параметрах Bluetooth Windows — повторить п. 2.
5. Убрать в кейс, закрыть крышку на 10 с, достать — повторить п. 2.
Если в п. 2 Off не появился, а результат был «sent, no answer», AirPods команду не применили или требуют другого
порядка; повторять запись автоматически приложение не будет.

## 6. Команды

```
airpodsctl bridge-check                      адаптер и устройства ввода, ничего не отключает
```
